# ГОСТ Analyzer

ГОСТ Analyzer — веб-приложение для автоматического анализа, генерации и оформления учебных отчётов.

Пользователь загружает исходный документ, указывает тему работы и необходимые данные, после чего система анализирует содержимое, определяет структуру документа, предлагает недостающие разделы с использованием LLM/ML-модуля и формирует итоговый документ с применением правил оформления.

Результат можно получить в формате DOCX или PDF.

---

## Возможности

- регистрация и авторизация пользователей;
- создание и хранение проектов;
- загрузка DOCX-документов;
- анализ структуры отчёта;
- определение недостающих разделов;
- генерация текста с помощью LLM;
- анализ изображений и OCR;
- генерация подписей к изображениям;
- создание титульного листа;
- применение базовых правил оформления ГОСТ;
- сборка итогового DOCX;
- экспорт документа в PDF;
- просмотр истории проектов.

## Git Workflow

В проекте используются две основные ветки:

```text
main
dev
```

### main

Содержит стабильную версию проекта.

Прямые изменения в `main` не выполняются.

Изменения попадают в `main` только после проверки общей версии проекта.

### dev

Основная интеграционная ветка разработки.

Все рабочие ветки создаются от `dev`.

После завершения задачи создаётся Pull Request обратно в `dev`.

---

## Рабочие ветки

Для каждой задачи создаётся отдельная ветка.

Примеры:

```text
feature/BE-01-jwt-auth
feature/FR-01-api-sync
feature/DOC-01-document-processing
feature/ML-01-api-contract

fix/BE-02-tests

infra/DO-01-docker

test/QA-01-regression-tests

chore/repository-setup
```

Используемые префиксы:

```text
feature/    новая функциональность
fix/        исправление ошибки
infra/      DevOps и инфраструктура
test/       тестирование
docs/       документация
chore/      технические изменения репозитория
```

## Процесс разработки

Стандартный процесс выполнения задачи:

```text
Получение задачи
        ↓
Создание ветки от dev
        ↓
Разработка
        ↓
Локальная проверка
        ↓
Commit
        ↓
Push
        ↓
Pull Request в dev
        ↓
Code Review
        ↓
QA
        ↓
Merge в dev
```

Пример:

```bash
git switch dev
git pull

git switch -c feature/BE-01-jwt-auth
```

После выполнения работы:

```bash
git add .
git commit -m "feat: use JWT ownership for projects"
git push -u origin feature/BE-01-jwt-auth
```

После этого создаётся Pull Request:

```text
feature/BE-01-jwt-auth → dev
```

## Правила Pull Request

Каждый Pull Request должен содержать:

- название задачи;
- краткое описание изменений;
- что было сделано;
- как проверить изменения;
- ссылку на Issue;
- информацию о тестировании.

Pull Request не должен объединяться, если:

- код не запускается;
- тесты не проходят;
- есть критические замечания;
- задача не соответствует требованиям;
- изменения не были проверены.

---

## Definition of Done

Задача считается выполненной, если:

- код написан;
- функциональность работает локально;
- обработаны основные ошибки;
- отсутствуют секреты и локальные пути;
- добавлены или обновлены тесты;
- обновлена документация при изменении API;
- создан Pull Request;
- Pull Request прошёл Code Review;
- тесты прошли успешно;
- QA проверил результат;
- изменения объединены в `dev`.

## Запуск проекта

Полный запуск через Docker Compose находится в разработке.

После завершения инфраструктурной части проект должен запускаться командой:

```bash
docker compose up --build
```

Планируемый запуск должен поднимать:

```text
Frontend
Backend
Doc Service
ML Service
Database
Ollama
```

До завершения контейнеризации инструкции по локальному запуску отдельных сервисов находятся в соответствующих каталогах.

## Переменные окружения

Реальные `.env` файлы не хранятся в Git.

Для каждого сервиса используется шаблон:

```text

```

Перед локальным запуском разработчик создаёт собственный `.env`.

Пример:

```bash
cp .env.example .env
```
